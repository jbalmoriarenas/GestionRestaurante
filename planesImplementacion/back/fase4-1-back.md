# Plan de Implementación — Fase 4.1 (Backend): Valoraciones — conexión OAuth con Google y sincronización de reseñas

Reutiliza el modelo de datos de [`../bbdd/fase4-1-bbdd.md`](../bbdd/fase4-1-bbdd.md) (tablas `conexion_google_business`, `valoraciones`). Introduce en el proyecto, por primera vez: un flujo **OAuth 2.0** contra un proveedor externo, una **tarea programada** (`@Scheduled`) y **cifrado de un dato en reposo**. Expone el contrato que consume [`../front/fase4-1-front.md`](../front/fase4-1-front.md).

## Contexto y objetivo

Endpoints para que el Admin: (a) conecte la cuenta de Google Business Profile del restaurante ("Sidrería La Zapica") vía OAuth; (b) consulte el estado de esa conexión (conectada/desconectada, última sincronización, último error); (c) fuerce una sincronización manual; (d) desconecte la cuenta. Una tarea programada sincroniza las reseñas automáticamente en segundo plano mientras la conexión esté activa. El listado/resumen de reseñas ya sincronizadas es [`fase4-2-back.md`](./fase4-2-back.md), que solo lee lo que este documento guarda.

> **"Tiempo real" del enunciado del usuario**: Google no ofrece un stream de reseñas nuevas. Se interpreta (acordado con el usuario en la conversación de planificación) como sincronización periódica automática (job programado, por defecto cada 6h) más un botón de sincronización manual bajo demanda — nunca una consulta directa a Google en el momento de ver el listado. El front siempre lee de `valoraciones` (BBDD), nunca de la API de Google.

## Análisis y decisión de autorización

Igual que `fase3-1-back.md` con `NOMINAS:EDICION`: la vista `VALORACIONES` ya es de edición exclusiva de `ADMIN` desde `bbdd/fase4-1-bbdd.md` (`V38`) — `EMPLEADO` no tiene ninguna fila de permiso para `VALORACIONES`. Todos los endpoints de este documento se protegen con `@PreAuthorize("hasAuthority('VALORACIONES:EDICION')")`, **con una única excepción**: `GET /api/valoraciones/conexion/callback` (ver "Decisiones técnicas" — Google redirige el navegador ahí directamente, sin ningún JWT).

## Análisis y supuestos

- **Se asume una única ubicación de Google Business Profile por cuenta conectada** (el restaurante). Si el descubrimiento de ubicaciones (paso 4 más abajo) devolviera más de una, se conecta automáticamente la primera y se deja constancia en el nombre mostrado — no se construye un selector de ubicación en esta fase al no ser un caso de uso confirmado; revisar si en la práctica la cuenta gestiona varias ubicaciones.
- **Solo se pide acceso de lectura de reseñas**, nunca de escritura (no hay endpoint para responder a una reseña desde la app, no solicitado por el usuario) — el scope de OAuth solicitado (`business.manage`, el único que expone la API de reseñas) técnicamente permite más que leer, pero la app nunca usa esa capacidad; documentado explícitamente para que quede claro que es una limitación de la API de Google, no una intención de este módulo.
- **Despliegue de una sola instancia** (mismo supuesto ya asumido en `plan-implementacion-general.md`): el estado efímero del flujo OAuth (ver punto 3) se guarda en memoria del propio proceso, no en BBDD ni en una caché distribuida.
- **La aprobación de acceso a la API de Google (Business Profile / "Google My Business API v4") puede tardar días** (Google la revisa manualmente) — no es un prerequisito bloqueante para construir el código de esta fase (se puede desarrollar y probar contra un proyecto de Google Cloud en modo de pruebas con cuentas de prueba autorizadas explícitamente), pero sí lo es para el uso en producción con la cuenta real del restaurante.

## Desglose de subtareas

### Modelo y cifrado
1. **[Backend, baja]** Entidad `ConexionGoogleBusiness` (`@Id` fijo a `1L`, sin `@GeneratedValue`): `id`, `locationResourceName`, `nombreUbicacion` (nullable), `refreshTokenCifrado`, `fechaConexion`, `conectadoPorAdminId`, `fechaUltimaSincronizacion` (nullable), `ultimoError` (nullable). `ConexionGoogleBusinessRepository extends JpaRepository<ConexionGoogleBusiness, Long>`: `findById(1L)` es el único acceso real (documentado como convención del propio servicio, no una restricción del repositorio).
2. **[Backend, baja]** Entidad `Valoracion`: `id`, `googleReviewId`, `autorNombre`, `autorFotoUrl` (nullable), `puntuacion: Integer`, `comentario` (nullable), `fechaPublicacion`, `fechaActualizacion` (nullable), `fechaSincronizacion`. `ValoracionRepository extends JpaRepository<Valoracion, Long>`: `findByGoogleReviewId(String): Optional<Valoracion>` (para el *upsert* de sincronización).
3. **[Backend, media]** `TokenEncryptionService`: `cifrar(String textoPlano): String` / `descifrar(String cifrado): String`, AES/GCM con una clave simétrica de 256 bits leída de `app.google.token-encryption-key` (Base64, **sin valor por defecto** — a diferencia de `app.jwt.secret`, que sí trae uno de ejemplo en `application.properties`: un refresh token de Google es más sensible y no debe arrancar nunca con una clave conocida/de ejemplo, así que el arranque falla explícitamente si la variable no está definida). Primera vez que el proyecto cifra un dato en reposo.

### Flujo OAuth
4. **[Backend, alta]** `GoogleBusinessProfileClient` (interfaz, misma filosofía que `FacturaExtractionService`/`FileStorageService`: aísla las llamadas HTTP a Google detrás de una abstracción, testeable con un mock):
   - `generarUrlConsentimiento(String state): String` — construye la URL de `accounts.google.com/o/oauth2/v2/auth` con `client_id`, `redirect_uri`, `scope=https://www.googleapis.com/auth/business.manage`, `access_type=offline` (imprescindible para que Google devuelva un `refresh_token`, no solo un `access_token`), `prompt=consent` (fuerza a Google a reemitir el `refresh_token` aunque el Admin ya hubiera autorizado antes) y el `state` recibido.
   - `intercambiarCodigoPorTokens(String code): TokensGoogle {accessToken, refreshToken, expiraEnSegundos}` — `POST` a `oauth2.googleapis.com/token`.
   - `refrescarAccessToken(String refreshToken): String` — mismo endpoint, `grant_type=refresh_token`; se llama antes de cada operación contra la API de reseñas (un `access_token` dura ~1h, no se persiste, se pide uno nuevo cada vez que hace falta).
   - `listarUbicaciones(String accessToken): List<UbicacionGoogle {locationResourceName, nombre}>` — `GET` a la API de gestión de cuentas de Google Business Profile, para descubrir qué ubicación(es) gestiona la cuenta que acaba de autorizar.
   - `listarReseñas(String accessToken, String locationResourceName, String pageToken): PaginaReseñasGoogle {reseñas, siguientePageToken}` — `GET accounts/{accountId}/locations/{locationId}/reviews` (Google My Business API v4, la única superficie de la API de Google Business Profile que expone reseñas), paginado vía `pageToken`.
   - `revocarToken(String refreshToken): void` — `POST` a `oauth2.googleapis.com/revoke`, *best-effort* (ver punto 9).
5. **[Backend, media]** `GoogleBusinessProfileClientImpl implements GoogleBusinessProfileClient`: llamadas HTTP directas vía `RestClient` de Spring — **sin** el SDK oficial de Google (`google-api-client`), ver "Decisiones técnicas".
6. **[Backend, media]** `ConexionGoogleService.iniciarConexion(Long adminId): String` (devuelve la URL de consentimiento): genera un `state` aleatorio (UUID), lo guarda en un mapa en memoria (`ConcurrentHashMap<String, PendingState>`, `PendingState{adminId, expiraEn}`, TTL 10 minutos — ver "Análisis y supuestos" sobre despliegue de una sola instancia) junto con el `adminId` que lo solicitó, y delega en `GoogleBusinessProfileClient.generarUrlConsentimiento`.
7. **[Backend, alta]** `ConexionGoogleService.completarConexion(String code, String state): void` — valida que `state` exista en el mapa en memoria y no haya expirado (si no, `EstadoOAuthInvalidoException`, 400); intercambia `code` por tokens; llama a `listarUbicaciones` con el `accessToken` recibido (ver "Análisis y supuestos" sobre una única ubicación); cifra el `refreshToken` (`TokenEncryptionService`) y hace *upsert* de la fila `id = 1` en `conexion_google_business` (crea si no existe, sobrescribe si el Admin reconecta); dispara una primera sincronización inmediata (delega en el punto 10) para que el panel no aparezca vacío tras conectar.
8. **[Backend, baja]** `GET /api/valoraciones/conexion/url` → `{ urlConsentimiento: string }`, `@PreAuthorize("hasAuthority('VALORACIONES:EDICION')")`.
9. **[Backend, media]** `GET /api/valoraciones/conexion/callback?code=&state=` → **sin `@PreAuthorize`** (ver "Decisiones técnicas"), llama a `completarConexion` y responde con una redirección 302 al front: `<front-url>/valoraciones?conectado=true` en éxito, `<front-url>/valoraciones?error=<codigo>` si `completarConexion` lanza excepción (state inválido/expirado, fallo de Google, etc.) — nunca expone el error crudo en la URL.
10. **[Backend, baja]** `ConexionGoogleService.desconectar(): void` — si existe la fila `id = 1`: descifra el `refreshToken`, llama a `GoogleBusinessProfileClient.revocarToken` (*best-effort*: si falla, se registra y se continúa igualmente, mismo criterio que el ZIP de facturas con un archivo ilegible, `back/fase2-2-back.md`) y borra la fila. `DELETE /api/valoraciones/conexion` → 204, `@PreAuthorize("hasAuthority('VALORACIONES:EDICION')")`.

### Sincronización
11. **[Backend, alta]** `ValoracionSincronizacionService.sincronizar(): ResultadoSincronizacion {nuevas, actualizadas, total}`: si no existe fila en `conexion_google_business`, no hace nada (no es un error, simplemente no hay conexión); si existe, descifra el `refreshToken`, pide un `accessToken` nuevo (`refrescarAccessToken`), pagina `listarReseñas` hasta agotar `pageToken`, y por cada reseña recibida hace *upsert* en `valoraciones` por `googleReviewId` (`findByGoogleReviewId`: si existe, actualiza `puntuacion`/`comentario`/`fechaActualizacion` si cambiaron; si no, crea la fila). Al terminar (éxito o fallo), actualiza `fechaUltimaSincronizacion`/`ultimoError` en la fila de conexión (`ultimoError = null` si fue bien). Cualquier excepción de red/API se atrapa aquí — nunca debe tumbar el job programado ni dejar `ultimoError` sin actualizar.
12. **[Backend, media]** `ValoracionSincronizacionScheduler`: `@Scheduled(cron = "${app.valoraciones.sync-cron:0 0 */6 * * *}")` (cada 6h por defecto, configurable) → delega en `ValoracionSincronizacionService.sincronizar()`. Requiere `@EnableScheduling` en la configuración de la app (primera tarea programada del proyecto).
13. **[Backend, baja]** `POST /api/valoraciones/sincronizar` → `ResultadoSincronizacion` (síncrono, reutiliza el mismo `ValoracionSincronizacionService`), `@PreAuthorize("hasAuthority('VALORACIONES:EDICION')")` — permite al Admin forzar una actualización sin esperar al ciclo de 6h.
14. **[Backend, baja]** `GET /api/valoraciones/conexion` → `ConexionEstadoDTO {conectado: boolean, nombreUbicacion, fechaConexion, fechaUltimaSincronizacion, ultimoError}` (todos los campos salvo `conectado` a `null` si no hay fila), `@PreAuthorize("hasAuthority('VALORACIONES:EDICION')")`.

### Transversal
15. **[Backend, baja]** Config nueva en `application.properties`: `app.google.client-id=${GOOGLE_CLIENT_ID}`, `app.google.client-secret=${GOOGLE_CLIENT_SECRET}`, `app.google.redirect-uri=${GOOGLE_REDIRECT_URI:http://localhost:8080/api/valoraciones/conexion/callback}`, `app.google.token-encryption-key=${GOOGLE_TOKEN_ENCRYPTION_KEY}`, `app.valoraciones.sync-cron=${VALORACIONES_SYNC_CRON:0 0 */6 * * *}`, `app.front.base-url=${FRONT_BASE_URL:http://localhost:4200}` (para construir la URL de redirección del callback).
16. **[Backend, baja]** Nuevas excepciones: `EstadoOAuthInvalidoException` (400), `ConexionGoogleNoDisponibleException` (503, cuando Google responde con error al intercambiar/refrescar tokens) — registradas en `GlobalExceptionHandler`.
17. **[Backend, media]** Tests `@WebMvcTest`: token `EMPLEADO` recibe 403 en todos los endpoints salvo `/callback` (público); `/conexion` sin conexión existente devuelve `conectado = false` con el resto de campos a `null`; `/conexion/callback` con un `state` no reconocido redirige (302) a `<front>/valoraciones?error=...` sin persistir nada (ver nota más abajo sobre por qué no responde 400).
18. **[Backend, media]** Tests unitarios de `ConexionGoogleService`/`ValoracionSincronizacionService` con `GoogleBusinessProfileClient` mockeado (**no** se llama a la API real de Google en tests, mismo criterio que Tesseract en `fase2-3-back.md`): `completarConexion` cifra el `refreshToken` antes de guardarlo; `sincronizar` hace *upsert* (no duplica) al procesar dos veces la misma reseña; `sincronizar` sin conexión no lanza excepción ni llama al cliente de Google.
19. **[Backend, baja]** Test unitario de `TokenEncryptionService`: cifrar y descifrar un texto de prueba devuelve el original; el texto cifrado no contiene el texto plano.

## Decisiones técnicas

- **`GET /api/valoraciones/conexion/callback` es el único endpoint de todo el proyecto sin `@PreAuthorize`** (se añade a la lista de rutas públicas de Spring Security junto a `/api/auth/login`): Google redirige el navegador del Admin directamente a esta URL tras el consentimiento, una navegación de página completa que **no** lleva el header `Authorization` que añade el interceptor HTTP del front — no hay forma de exigir un JWT ahí. La seguridad de este endpoint no depende de autenticación, sino de que `state` sea un valor aleatorio de un solo uso, con TTL corto, generado únicamente por una llamada previa ya autenticada a `/conexion/url` — mismo principio de "estado" (*state* parameter) que exige el propio estándar OAuth 2.0 para mitigar CSRF, aquí reutilizado además para saber qué Admin inició el flujo.
- **`state` en memoria (`ConcurrentHashMap`), no en BBDD**: es un dato puramente efímero (TTL de 10 minutos) que no aporta nada persistir — evita una tabla nueva solo para esto. Coherente con el supuesto ya documentado de despliegue de una sola instancia; si el proyecto pasara a varias instancias, este mapa tendría que moverse a una caché compartida (Redis o similar), no antes.
- **`access_token` nunca se persiste, se pide uno nuevo en cada sincronización**: vive ~1h y solo se usa en el momento; guardarlo no ahorra nada relevante (el *refresh* es una llamada HTTP barata) y sería un dato sensible más que proteger en reposo sin necesidad.
- **Cifrado simétrico (AES/GCM) con clave fuera de BBDD, en vez de un `KeyStore`/gestor de secretos dedicado**: para el tamaño y la infraestructura actual del proyecto (un servidor, sin Vault ni AWS KMS en la arquitectura) una clave en variable de entorno es coherente con cómo ya se gestionan `DB_PASSWORD`/`app.jwt.secret`; revisar si el proyecto migra a un entorno con gestor de secretos propio.
- **Llamadas HTTP directas a la API de Google (`RestClient`) en vez del SDK oficial (`google-api-client` + los *services* generados)**: la superficie de API que se necesita es pequeña (4-5 endpoints REST bien documentados) — añadir el SDK completo (con sus propias dependencias de autenticación, distintas del flujo OAuth manual ya construido aquí) sería más peso y una segunda forma de hacer lo mismo, sin aportar valor proporcional. Mismo criterio de dependencias acotadas ya aplicado en Fase 2.3 (Tess4J + PDFBox, nada más de lo estrictamente necesario).
- **Primera sincronización inmediata tras conectar** (punto 7), en vez de esperar al primer ciclo programado (hasta 6h de espera): el Admin espera ver resultado inmediato tras conectar la cuenta, coherente con el criterio de UX ya aplicado en el resto del proyecto (p. ej. refrescar tablas tras una acción en vez de esperar a la siguiente carga).
- **Desconexión con revocación *best-effort***: si Google no responde al revocar, se borra igualmente la fila local (el Admin ya no puede sincronizar desde la app) — la alternativa, bloquear la desconexión hasta que Google confirme la revocación, dejaría al Admin sin forma de "olvidar" la conexión local si Google está caído.

## Riesgos y dependencias

- **Dependencia dura** con `bbdd/fase4-1-bbdd.md`: sin sus tablas, ningún endpoint de este documento tiene dónde persistir nada.
- **Riesgo alto — aprobación de acceso de Google**: la API de reseñas (Google My Business API v4) no está abierta por defecto a cualquier proyecto de Google Cloud; requiere solicitar acceso y que Google lo apruebe manualmente, lo que puede tardar días. No bloquea el desarrollo (se puede probar con cuentas de prueba autorizadas explícitamente en modo de pruebas de OAuth) pero sí el uso en producción con la cuenta real del restaurante — a iniciar el trámite lo antes posible, en paralelo a la construcción del resto de la fase.
- **Riesgo medio — dependencia de un servicio externo fuera de control del proyecto**: si Google cambia límites de cuota, deprecia la API (ya ocurrió una vez con la primera versión de "Google My Business API") o el negocio revoca el acceso desde su propia cuenta de Google, la sincronización empieza a fallar; mitigado por `ultimoError` visible en el panel de conexión (`fase4-1-front.md`) y porque el fallo nunca tumba el resto de la app (aislado en `ValoracionSincronizacionService`).
- **Riesgo medio — clave de cifrado del refresh token**: si se pierde `GOOGLE_TOKEN_ENCRYPTION_KEY` en producción, el token guardado queda irrecuperable y hay que reconectar manualmente — no hay backup automático de esta clave (fuera de alcance de este documento, política de despliegue).
- **Riesgo bajo**: el `state` en memoria no sobrevive a un reinicio del backend — si el Admin inicia el flujo justo antes de un despliegue, tendría que reintentarlo; aceptable (una reconexión manual, sin pérdida de datos).

## Criterios de aceptación técnicos

- `GET /api/valoraciones/conexion` sin ninguna fila en `conexion_google_business` devuelve `conectado = false` y el resto de campos `null`.
- Completar el flujo OAuth con un `code`/`state` válidos crea la fila `id = 1` con el `refreshToken` cifrado (nunca en texto plano en BBDD) y dispara una sincronización inmediata.
- Llamar a `/conexion/callback` con un `state` no emitido por `/conexion/url` (o ya expirado) redirige (302) a `<front>/valoraciones?error=...` sin crear ninguna fila — nunca un 400 crudo: el endpoint lo recibe siempre un navegador a mitad de una redirección de Google, así que cualquier fallo (`EstadoOAuthInvalidoException` incluida) se traduce en una redirección de vuelta al front con el error en la query, no en una respuesta JSON que el usuario vería en crudo (revisión durante la implementación respecto al criterio original de este documento).
- `POST /api/valoraciones/sincronizar` sin conexión activa no falla (responde con `{nuevas: 0, actualizadas: 0, total: 0}` o equivalente), no intenta llamar a Google.
- Sincronizar dos veces seguidas la misma reseña de Google no duplica la fila en `valoraciones` (mismo `googleReviewId`).
- `DELETE /api/valoraciones/conexion` borra la fila de conexión aunque la llamada de revocación a Google falle.
- Un fallo de red/API de Google durante la sincronización programada queda registrado en `ultimoError`, sin lanzar ninguna excepción no controlada ni afectar a otros endpoints de la app.
- Un token `EMPLEADO` recibe 403 en todos los endpoints de este documento excepto `/conexion/callback`.
